## 2. 需求澄清结果

### 2.1 需求与概念

用户目标是让 logger 初始化成功后的日志目录提示在目录路径末尾显示目录分隔符，分隔符允许为 `\\` 或 `/`。目标角色为开发者，业务价值是让目录与后续日志文件名边界清晰，便于直接定位日志位置。当前需求是 Sprint01/US-003 的相关增量，不改写 US-003 的历史原始需求。

### 2.2 边界与约束候选

**确认事实**：

- 当前提示由 `src/custom_logger/manager.py` 的 `init_custom_logger_system` 在 `_initialized = True` 之后通过 `logger.info` 输出。
- 当前提示同时包含目录值、`full.log` 和 `warning.log`，本 issue 只要求目录字符串的结尾格式变化。
- 当前登记明确涉及一个生产文件和一个对应测试文件：`src/custom_logger/manager.py`、`tests/01_unit_tests/test_tc0030_init_log_path.py`。
- 当前 Sprint 运营行无明确依赖、无文件冲突，状态为 `待办`。

**约束候选**：

- 保持低耦合高内聚代码复用，同一目录格式化逻辑只维护一份。
- 不改变 `config.paths.log_dir` 的存储值，格式化只作用于初始化成功提示的显示边界。
- 不改变 `logger.info` 的日志级别、初始化时序、日志文件名或 writer/queue 的文件创建行为。
- 运行平台原生分隔符是实现推荐；用户可接受的业务结果仍是以 `\\` 或 `/` 结尾。

| 登记歧义 | 分类 | 当前结论 | 是否 material_user_decision_gap |
|:---|:---|:---|:---|

| 已带分隔符时是否禁止重复 | non-material implementation boundary | 采用最小充分行为：显示值保持恰好一个结尾分隔符，避免路径观感和拼接歧义 | 否 |
| 是否扩展到所有日志目录输出 | explicit_scope | 仅约束 US-003 的初始化成功提示；其他目录输出不在本 issue 范围 | 否 |

### 2.4 验收标准基线

登记阶段的初步标准为：初始化成功后的日志目录输出以 `\\` 或 `/` 结尾；目录与 `full.log`、`warning.log` 文件名同时保留；端到端测试通过。本阶段将其细化为 `#8` 的最终验收标准，登记区块不回写覆盖。

## 3. 综合方案分析

这个需求的最小充分结果是改变初始化成功提示中的一个显示边界，而不是改变路径对象、配置契约或日志文件创建流程。当前实现已经把提示放在普通模式和队列模式的初始化分支收敛点之后，因此将规范化限制在提示构造处可以保持职责边界：路径来源仍由现有配置提供，writer 和 queue 继续消费原始路径，logger 继续承担输出。相比把分隔符写回配置或上移到所有路径生产处，输出边界处理的影响面更小、可逆性更好，也能让已有配置值保持兼容。实现上应先移除末尾已有的 `/` 或 `\\`，再补一个运行平台分隔符，避免重复；该判断属于显示格式规则，不应散落在多个调用点。由于本 issue 只有一个用户可观察结果、一个生产调用点和一个回归测试边界，不满足并行实施或独立验收拆分门槛，保留为单一纵向切片。需要运行时确认的普通/队列模式输出、已有分隔符去重和测试隔离均交由 `design-plan` 验证，不在本阶段宣称已验证。

## 4. 方案探索与纵向切片

### 4.1 可行候选集与推荐方案

严格按用户目标、现有代码边界和低耦合约束过滤后，仅保留一个可行候选：

**方案 A（推荐）：在初始化提示输出边界规范化目录显示值**

- 在 `init_custom_logger_system` 的统一提示构造处生成显示值。
- 处理顺序为：将目录值转为显示字符串，去掉已有的 `/` 与 `\\` 结尾，再追加运行平台分隔符；不写回配置对象。
- 保留现有 `logger.info`、初始化时序、普通/队列分支收敛点和日志文件名文本。
- 在 `test_tc0030_init_log_path.py` 增加目录结尾和去重断言，覆盖无分隔符、已有 `/`、已有 `\\` 的输入边界；具体测试组织和运行证据由 `design-plan` 冻结。

**显式排除的方向**：

- 方案 B：修改 `config.paths.log_dir` 或 writer 的路径生产契约，使所有消费者都接收带分隔符路径。该方向扩大影响面，可能改变文件创建和其他调用方行为，不符合本 issue 的最小范围。
- 方案 C：直接固定拼接 `/` 或 `\\`。该方向不能同时保证平台一致性和已有分隔符去重，且会把格式规则写成脆弱的字符串特例。

### 4.2 纵向切片与前置依赖

## 6. 约束集

### 6.1 硬约束

- 初始化成功后仍使用现有 `logger.info` 输出。
- 输出中的目录显示值以 `\\` 或 `/` 结尾，且规范化后只保留一个结尾分隔符。
- `full.log` 与 `warning.log` 文件名信息保留。
- 普通模式与队列模式的初始化时序和失败语义不改变。
- 生产代码和测试代码保持低耦合高内聚，同一格式化逻辑只维护一份。

### 6.2 软约束

- 优先使用运行平台原生分隔符，保持开发者在本机看到的路径风格一致。
- 不改变 `config.paths.log_dir` 的对象值，避免影响其他消费者。
- 测试应覆盖已有结尾分隔符，避免输出出现双分隔符。

### 6.3 明确排除的方向

- 不重构 writer、queue writer 或配置对象的路径契约。
- 不把分隔符追加到文件名或修改 `full.log`/`warning.log` 名称。
- 不扩展到所有日志目录输出，不改变其他模块日志消息。
- 不新增架构层、公共 API 或前端原型。

### 6.4 技术约束

- Python 生产代码采用现有函数职责边界；本地格式化不需要引入新的类或跨模块抽象。该判断保留 OOP 偏好审计：当前没有独立状态、生命周期或测试隔离收益足以支持新对象边界，design-plan 需确认实现不会把逻辑复制到多个调用点。
- 物理行数阈值证据登记为 `unknown`，本阶段不执行规模统计；design-plan/implementation 按实际文件证据回填，不以未知触发拆分。
- 需要运行命令才能确认的兼容性、输出和测试主张统一列入 `#9.1`。

### 6.5 数据闭环约束

- 不涉及数据采集、持久化、离线分析或产出回灌；无需新增数据闭环。
