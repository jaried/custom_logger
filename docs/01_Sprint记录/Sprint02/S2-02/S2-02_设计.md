## `get_caller_info()` 精确控制流

实施不得重新组织为第二个生产 helper。`get_caller_info()` 内固定使用以下局部状态：

- `frame = None`：`inspect.currentframe()` 的起始 frame 引用。
- `current_frame = None`：当前扫描 frame 引用。
- `show_call_chain: bool = False`。
- `in_test: bool = False`。
- `caller: Optional[Tuple[str, int]] = None`，只保存字符串与整数。
- `last_custom_logger_frame: Optional[Tuple[str, int]] = None`，只保存字符串与整数。

固定控制流如下：

1. `frame`、`current_frame` 先置 `None`，随后进入同一个外层 `try / except Exception / finally`。
2. 执行 `frame = inspect.currentframe()`；若为 `None`，直接返回 `("main", 0)`，`finally` 仍必须执行。
3. 执行 `current_frame = frame.f_back`。
4. 按当前语义读取一次 `show_call_chain`：调用 `get_config()`；读取失败保持 `False`，不得让配置读取失败阻止 caller 定位。
5. 使用 `while current_frame is not None` 做唯一一次上游扫描；不得构造 frame list，不得二次遍历。
6. 每个 frame 先读取 `filename = current_frame.f_code.co_filename`、`line_number = current_frame.f_lineno`、`basename = os.path.basename(filename)`；在任何 caller 过滤之前检查 `"test_tc" in filename`，命中即设置 `in_test=True`。
7. 只有当 `caller is None` 且 `0 < line_number <= 10_000` 时参与 caller 选择。
8. 若 `os.path.splitext(basename)[0].startswith("test_tc")`，把 `caller` 固定为 `("test_tc0", line_number)`，后续 frame 不得覆盖。
9. 否则按现有表达式计算 custom_logger 内部 frame：规范化路径包含 `custom_logger`，且 basename 属于 `logger.py`、`formatter.py`、`writer.py`、`config.py`、`manager.py`，或 basename 以 `module` / `internal` 开头。命中时仅覆盖 `last_custom_logger_frame=(name_without_ext, line_number)`。
10. 非内部 frame 再使用现有 `framework_files` 集合与 `basename == "<string>"` 判断；集合内容不增删。
11. `name_without_ext.lower()` 包含 `mock` 时继续跳过，语义不变。
12. 第一个通过全部过滤的 frame 把 `caller` 固定为 `(name_without_ext[:16], line_number)`。
13. 无论是否已经得到 `caller`，每轮末尾只执行 `current_frame = current_frame.f_back`，继续直到 `None`；继续扫描仅用于保持 `in_test` 诊断语义。
14. 扫描完成后先处理 `show_call_chain`：为真时调用既有 `_get_call_stack_info()` 并输出 `[调用链] ...`。
15. 若 `in_test=True`，再次按现有方式读取 `get_config().show_debug_call_stack`；为真时调用 `_get_call_stack_info()` 并输出 `DEBUG: get_caller_info调用链: ...`。
16. 返回优先级固定为：`caller` → `last_custom_logger_frame`（返回前模块名截断 16 字符）→ `("unknown", 0)`。
17. 任意 frame 获取、访问或扫描异常进入现有异常语义：再次尝试读取 `show_call_chain`；开启时输出 `[调用链异常] {e}`；返回 `("error", 0)`。
18. `finally` 中必须显式 `del current_frame`、`del frame`；任何路径都不得让 frame 对象进入 tuple、list、闭包、全局状态或返回值。
19. 不新增 `next_frame`、frame 容器、caller 缓存、生产 helper、Adapter 或第二 Seam。
20. `get_call_stack()`、`get_exception_info()`、`logger.py::_log()` 和配置字段不改；`LEGACY-S2-02-01` 保持显式未解决。

## Codebase Design 落点

- **Module**：`get_caller_info()`。
- **Interface**：`get_caller_info() -> Tuple[str, int]` 及其既有过滤、失败与性能契约。
- **Seam**：`create_log_line()` → `get_caller_info()`，位置不移动。
- **Implementation**：仅从 `inspect.stack()` 替换为 raw frame 单次扫描。
- **Adapter**：不新增；不存在第二种需要替换的 Implementation，不建立假想 Seam。
- **Depth**：caller 过滤、fallback、失败语义、诊断条件继续隐藏在单一 Interface 后面。
- **Locality**：caller 规则继续只由 `formatter.py` owner 持有，不散入 logger、writer、queue 或调用方。
- **Test surface**：测试跨现有 `get_caller_info()` / `create_log_line()` Interface，不暴露 private scanner，不新增测试专用生产入口。

## 迁移、兼容与恢复

- 无配置、数据、日志格式或持久文件迁移。
- 生产回滚单位仅为 `formatter.py::get_caller_info()` 的 Implementation；对应测试与 benchmark 资产随同回滚。
- `logger.py`、`config.py`、writer、queue 无迁移、兼容层或恢复动作。
- `LEGACY-S2-02-01` 保持未解决；S2-02 不得借回归修复该遗留。

## 性能与资源设计

benchmark 文件：`docs/05_预研/验证_20260915/benchmark_s2_02_caller_info.py`。

固定命令形态：

```text
D:/anaconda3/envs/base_python3.12/python.exe docs/05_预研/验证_20260915/benchmark_s2_02_caller_info.py --source-root <repo_root> --git-ref <sha> --output <json_path>
```

脚本必须在导入 `custom_logger` 前把 `<source-root>/src` 插入 `sys.path[0]`，确保独立 Python 进程加载指定 ref 的源码，而不是其他 editable 路径。

固定场景：

- **Case A**：测量函数直接循环调用 `get_caller_info()`。
- **Case B**：增加一层外部 probe 后进入测量函数，使 frame 深度增加一层；不包装 `logger.<level>()`。

正确性断言全部在计时前完成。初始化、teardown、配置构造、import、JSON 写入与结果断言均在计时范围外。

每个 Git ref、每个 Case 固定：

1. 预热 `10_000` 次。
2. `7` 个独立 round。
3. 每个 round `100_000` 次调用。
4. `time.perf_counter_ns()` 记录每个 round 总纳秒，换算 `ns/call`。
5. 使用 `statistics.median` 计算 median，并保存 min、max 与所有 round 原始值。

baseline ref 固定为 `1e6f7c19c6666ec988efb70633166127479e2007`。baseline 使用 detached 临时 worktree `../custom_logger_s2_02_baseline`，不创建分支；candidate 使用 Implementation 完成后的当前 HEAD。两者执行主 worktree 中同一份 benchmark 脚本，只改变 `--source-root`、`--git-ref` 和输出文件，并使用两个独立 Python 进程。完成后删除临时 worktree。

性能通过条件：**Case A 与 Case B 的 candidate median `ns/call` 都必须严格低于对应 baseline median**。不设置未经测量的百分比目标。

输出资产：

- `S2-02_benchmark_baseline.json`
- `S2-02_benchmark_candidate.json`
- `S2-02_benchmark_report.md`

报告固定记录解释器、平台、baseline/candidate SHA、两个 JSON 路径、Case A/B 的 baseline median、candidate median、差值与 pass/fail。
