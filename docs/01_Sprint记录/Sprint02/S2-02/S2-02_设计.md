### `get_caller_info()` 精确控制流

实施不得重新组织为第二个生产 helper。`get_caller_info()` 内固定使用以下局部状态：

- `frame`：`inspect.currentframe()` 的起始 frame 引用，初始为 `None`。
- `current_frame`：当前扫描 frame 引用，初始为 `None`。
- `show_call_chain: bool = False`。
- `in_test: bool = False`。
- `caller: Optional[Tuple[str, int]] = None`，只保存字符串与整数。
- `last_custom_logger_frame: Optional[Tuple[str, int]] = None`，只保存字符串与整数。

固定控制流：

1. `frame`、`current_frame` 先置 `None`，随后进入同一个外层 `try / except Exception / finally`。
2. `frame = inspect.currentframe()`；若为 `None`，直接返回 `("main", 0)`，`finally` 仍执行。
3. `current_frame = frame.f_back`。
4. 按当前语义读取一次 `show_call_chain`：调用 `get_config()`，读取失败保持 `False`，不得让配置读取失败阻止 caller 定位。
5. `while current_frame is not None` 做唯一一次上游扫描；不得构造 frame list、不得二次遍历。
6. 每个 frame 先读取 `filename = current_frame.f_code.co_filename`、`line_number = current_frame.f_lineno`、`basename`；在任何 caller 过滤之前执行 `"test_tc" in filename`，命中即把 `in_test=True`。
7. 只有当 `caller is None` 且 `0 < line_number <= 10_000` 时参与 caller 选择：
   - `name_without_ext.startswith("test_tc")`：把 `caller` 固定为 `("test_tc0", line_number)`。
   - 否则按现有表达式计算 `is_custom_logger_file`；命中时仅覆盖 `last_custom_logger_frame=(name_without_ext, line_number)`。
   - 非内部 frame 再按现有 `framework_files` 集合、`basename == "<string>"` 与 `"mock" in name_without_ext.lower()` 过滤。
   - 首个通过全部过滤的 frame 把 `caller` 固定为 `(name_without_ext[:16], line_number)`。
8. 无论是否已经得到 `caller`，本轮末尾只执行 `current_frame = current_frame.f_back`，继续直到 `None`；后续 frame 不得覆盖 `caller`。
9. 扫描完成后先处理 `show_call_chain`：为真时调用 `_get_call_stack_info()` 并输出 `[调用链] ...`。
10. 若 `in_test=True`，再次按现有方式读取 `get_config().show_debug_call_stack`；为真时调用 `_get_call_stack_info()` 并输出 `DEBUG: get_caller_info调用链: ...`。
11. 返回顺序固定：`caller` -> `last_custom_logger_frame`（返回前模块名截断 16 字符） -> `("unknown", 0)`。
12. 任意 frame 获取/访问/扫描异常进入现有异常语义：再次尝试读取 `show_call_chain`；开启时输出 `[调用链异常] {e}`；返回 `("error", 0)`。
13. `finally` 中必须显式 `del current_frame`、`del frame`；任何路径都不得让 frame 对象进入 tuple/list/闭包/全局/返回值。
14. 不新增 `next_frame`、frame 容器或缓存；因此 raw-frame 生命周期只存在 `frame/current_frame` 两个局部引用。

### 测试文件精确结构

`tests/01_unit_tests/test_s2_02_caller_info.py` 使用项目既有测试风格，定义本地隔离配置对象，字段固定包含：

- `first_start_time=datetime.now()`；
- `paths={"log_dir": <tmp_path>}`；
- `logger.global_console_level="debug"`；
- `logger.global_file_level="debug"`；
- `logger.show_call_chain`；
- `logger.show_debug_call_stack`；
- `logger.show_warning_stack=False`；
- `logger.module_levels={}`。

fixture 负责 `init_custom_logger_system(config)`，并在 `finally`/fixture teardown 中调用 `tear_down_custom_logger_system()`；不读取或改写生产配置。

固定用例名称与义务：

1. `test_s2_02_direct_caller_location`：调用前用测试侧 frame 行号取得下一行期望值，直接调用 `get_caller_info()`；模块名断言为 `Path(__file__).stem[:16]`，行号精确相等。
2. `test_s2_02_nested_probe_location`：私有测试 helper `_probe_caller_info()` 直接调用 `get_caller_info()` 并返回结果与调用行；外层测试断言仍定位该 helper 内的实际 Interface 调用行。helper 不调用 logger。
3. `test_s2_02_create_log_line_location`：初始化配置后直接调用 `create_log_line(...)`，断言日志头包含当前测试模块截断值与该调用行；不改变 `module_name` 参数语义。
4. `test_s2_02_plain_path_ignores_inspect_stack_and_getframeinfo`：同时 patch `custom_logger.formatter.inspect.stack`、`inspect.getframeinfo` 为抛异常，直接 caller 仍正确。
5. `test_s2_02_currentframe_none_returns_main`：patch `inspect.currentframe` 返回 `None`，精确断言 `("main", 0)`。
6. `test_s2_02_currentframe_exception_returns_error`：关闭诊断时 patch `currentframe` 抛异常，断言 `("error", 0)`；同一用例或参数化分支开启 `show_call_chain` 后断言 stdout 含 `[调用链异常]`。
7. `test_s2_02_module_name_truncates_to_16_chars`：利用当前文件 stem 本身超过 16 字符，断言返回值恰为 `Path(__file__).stem[:16]`，不另造生产 seam。
8. `test_s2_02_disabled_diagnostics_emit_no_chain`：两个诊断开关均 false 时调用 caller，stdout 不含 `[调用链]` 和 `DEBUG: get_caller_info调用链:`。

`tests/01_unit_tests/test_tc0019_call_chain.py` 只修改 `test_tc0019_06_exception_call_chain` 的 patch 字符串和 mock 变量名；其他测试正文保持原样。

### 条件专项：架构与模块职责

- Module 仍是 `get_caller_info()`；Interface、Seam、调用 owner 均不移动。
- `create_log_line()` 仍是 caller 信息的唯一生产消费者；`CustomLogger._log()` 继续只消费格式化日志行，不读取 frame。
- 不新增 Adapter。只有一个 raw-frame Implementation，不建立假想可替换 seam。
- test surface 与 caller Interface 同源：测试直接跨 `get_caller_info()` / `create_log_line()`，不暴露 private scanner。
- code-craft 结论：`get_caller_info()` 的复杂控制流是同一个变化原因（caller 定位），继续留在该深 Module 内；不机械拆 helper。

### 条件专项：性能与资源

benchmark 脚本固定 CLI：

```text
D:/anaconda3/envs/base_python3.12/python.exe docs/05_预研/验证_20260915/benchmark_s2_02_caller_info.py --source-root <repo_root> --git-ref <sha> --output <json_path>
```

脚本在导入 `custom_logger` 前把 `<source-root>/src` 插入 `sys.path[0]`，确保每个独立 Python 进程加载指定 ref 的源码，而不是环境中其他 editable 路径。

脚本固定包含 `direct_probe` 与 `outer_probe -> inner_probe` 两类正确性 probe；正确性检查在计时前完成。计时实现使用两个 measure 函数：Case A 在一个测量函数内循环调用 `get_caller_info()`；Case B 额外经一层外部 probe 进入测量函数，使 frame 深度增加一层，但计时起止仍位于测量函数内部。初始化、teardown、配置构造、import、JSON 与断言全部在计时区间外。

报告 `S2-02_benchmark_report.md` 固定记录：解释器、平台、baseline/candidate SHA、两个 JSON 路径、Case A/B 的 baseline median、candidate median、差值与 pass/fail；只有两个 Case 的 candidate median 都严格小于 baseline median 时性能 gate 为 pass。
