## 2. 需求、术语与可观察结果

### 2.1 用户结果

日志系统的普通日志调用仍显示真实调用者的文件名和行号；直接调用与经过用户包装函数调用时，位置均对应实际日志调用点。开启调用链调试时，完整调用链继续按原配置输出；异常、警告和错误级别的堆栈行为保持现状。

### 2.2 稳定术语

- **调用者定位**：`get_caller_info()` 返回的 `(模块名, 行号)`。
- **完整调用链**：`show_call_chain` 或测试调试开关打开时，由 `_get_call_stack_info()` 输出的链路文本。
- **异常堆栈**：`get_exception_info()` 与 `get_call_stack()` 为 `ERROR` 及以上、`WARNING` 配置分支提供的文本。

### 2.3 范围与非目标

本 Issue 只优化普通调用者定位的实现路径。公开的 `get_caller_info() -> Tuple[str, int]`、`create_log_line()`、`CustomLogger` 方法、logger 名称、日志格式、完整调用链 helper、异常堆栈 helper、配置字段和文件写入流程保持原有职责与接口。

## 3. 已验证事实与关键未知

### 3.1 代码事实

1. `src/custom_logger/formatter.py::get_caller_info` 当前每次调用 `inspect.stack()`，随后读取 `FrameInfo.filename`、`lineno` 并执行过滤；`src/custom_logger/formatter.py::create_log_line` 在每条实际日志行生成时调用它。
2. 调用链为 `CustomLogger._log()` → `create_log_line()` → `get_caller_info()`；调用者信息在日志行生成前确定，队列/普通 writer 只消费已格式化日志行。
3. `_get_call_stack_info()`、`get_call_stack()` 和 `get_exception_info()` 是独立路径；前两者仅在配置/级别分支需要时执行，不是普通定位必须路径。
4. 现有定位规则包含：跳过 `custom_logger` 内部帧、跳过框架和 mock 帧、测试文件优先返回 `test_tc0`、模块名最多 16 个字符、无合适外部帧时回退到最后一个内部帧或默认值。
5. `tests/01_unit_tests/test_tc0019_call_chain.py` 覆盖两个调用链开关、调试输出、多层调用、配置对象兼容和定位异常；`tests/test_custom_logger/test_tc0022_dynamic_module_name.py` 覆盖 logger 名称与调用模块行为；`tests/test_custom_logger/test_tc0021_error_stack_trace.py` 覆盖异常、警告和错误堆栈行为。

### 3.2 性能事实

消费项目的 py-spy 0.4.2 采样文件 `D:\quant_data\tqsdk_config\2026\09\14\tqsdk_config_20260914_230928.speedscope.json` 共 1,905 个样本；`get_caller_info()` 约占 0.92 采样秒，其中链路包含 `inspect.stack()`、`inspect.getframeinfo()` 和 `linecache.checkcache()`。该数据是场景采样权重，不是端到端等待时间，不能直接折算收益；本 Issue 必须在 custom_logger 内使用固定场景完成前后对照。

### 3.3 结构与工具事实

`codebase-design` 复核：`formatter` 是现有 Module，`get_caller_info` 是稳定 Interface 和唯一外部 Seam，`create_log_line` 是其现有调用 owner；本方案不新增 Module、Adapter 或跨 Seam 接口。Runtime 的 GitNexus 辅助结果为 `runner_missing`，因此以上结构事实以源码、测试和历史设计文档直接补证，未把缺失的辅助索引当作代码不存在。

### 3.4 关键未知

优化后的实际收益、解释器差异和固定调用场景的前后耗时只能在目标环境测量，列入 `#9.1` 的下游验证；本阶段不承诺百分比收益。当前没有会改变方案方向的其他未知。

## 4. 综合方案分析

需求的最小充分差量是替换 `get_caller_info` 的栈对象构造方式，而不是改变日志调用链或新增缓存、状态和公共参数。原始 frame 直接提供 `f_code.co_filename`、`f_lineno` 和 `f_code.co_name`，能够复用现有过滤规则并避开 `inspect.stack()` 创建完整 `FrameInfo` 与源码上下文的路径。完整调用链和异常堆栈仍由各自 helper 在需要时生成，因此普通日志的优化不会削弱显式调试能力。

## 5. 方案选择与原子性

### 5.1 完整推荐方案

采用方案 A：在现有 `get_caller_info()` 内使用 `inspect.currentframe()` 取得当前 frame，再从 `f_back` 开始遍历原始 frame 链。

实施约束固定为：

1. 保持 `get_caller_info() -> Tuple[str, int]` 和 `create_log_line()` 的 Interface 不变；`logger.py` 不增加 `stacklevel`、参数袋或新入口。
2. 用 `f_code.co_filename`、`f_lineno`、`f_code.co_name` 替代 `FrameInfo` 属性，保留现有模块名截断、测试文件优先、内部/框架/mock 过滤、内部帧回退和默认值规则。
3. 保留 `show_call_chain`、`show_debug_call_stack` 的配置读取和输出文字；完整链路仍仅在对应开关打开时调用 `_get_call_stack_info()`。
4. 保留异常语义：定位失败仍返回 `("error", 0)`；开启调用链时仍输出 `[调用链异常]`；空 frame 链仍返回原有默认值。
5. 不改写配置对象，不修改 `get_call_stack()`、`get_exception_info()`、日志级别分支、队列传输和 writer 行为。
6. 增加直接/包装调用的文件名与行号回归测试；更新定位异常测试的注入 Seam；以现有调用链、动态模块名和异常堆栈测试做相关回归。
7. 使用一个固定的无 I/O benchmark 记录优化前后相同场景、解释器、输入、预热次数、重复次数、计时范围和统计值，并同时核对日志内容和调用位置。

**必要性闭环**：删除 frame 遍历会继续执行每条日志的完整 `inspect.stack()`，当前采样指出的同步开销和验收标准 1 仍失败；新增公共接口、缓存状态或跨模块抽象不能增加用户结果，因此不纳入本方案。现有 `formatter.get_caller_info` 是唯一职责 owner，直接复用该 Seam。

## 6. 约束、失败语义与下游边界

### 6.1 硬约束

- 普通定位路径不再构造完整 `inspect.stack()` 或读取每帧源码上下文。
- 直接调用与用户包装调用返回实际调用文件名和行号；模块名截断和现有过滤规则保持一致。
- `show_call_chain`、`show_debug_call_stack` 开关的输出条件、文字标记和完整链路内容保持一致。
- `WARNING` 的可选调用栈、`ERROR/CRITICAL/EXCEPTION` 的异常/调用栈优先级保持一致。
- `logger.name`、日志行格式、队列/普通 writer、配置对象和公开函数签名保持一致。
- 生产实现不新增依赖、持久状态、缓存失效规则或 ADR。

### 6.2 失败与回退

`inspect.currentframe()` 返回空 frame 时沿用空栈默认值；frame 访问或遍历发生异常时沿用 `("error", 0)`，并按 `show_call_chain` 输出异常提示。完整调用链 helper 自身失败时仍返回其现有占位文本；异常堆栈 helper 的错误处理不变。实现不得吞掉会阻止日志行生成的异常之外的异常，也不得把失败伪装成正确调用位置。

### 6.3 兼容与恢复

不涉及数据迁移、配置迁移或持久格式变化。若固定 benchmark 或位置回归不通过，回退仅限当前 `formatter.py` 的实现差量和对应测试，不改动 logger/writer/queue 契约；未通过时不进入待验收。

## 7. 最终验收标准

- **AC-S2-02-01 调用位置**：在普通配置下，直接调用和至少一层用户包装调用均返回正确的调用文件名与日志调用行号；`create_log_line` 生成的日志行包含同一位置，且 `logger.name` 未被改写。
- **AC-S2-02-02 调用链与异常语义**：`show_call_chain`、`show_debug_call_stack` 的开关行为与原有输出标记保持；`WARNING`、`ERROR`、`CRITICAL`、`EXCEPTION` 的调用栈/异常栈测试通过，配置关闭时不额外生成完整调用链。
- **AC-S2-02-03 性能对照**：在同一解释器、同一输入和同一固定直接/包装场景下，记录基线与候选的预热次数、重复次数、计时起止范围、统计值和环境；候选普通定位耗时相对基线下降，且结果内容与调用位置断言同时通过。报告明确采样值不等同端到端收益，不设置未经测量的百分比承诺。
- **AC-S2-02-04 接口与范围**：公开函数签名、日志格式、配置字段、writer/queue 路径和异常失败语义保持；变更仅落在方案 `#10` 列出的生产、回归和验证资产。

## 8. 测试与验证决定

### 8.1 聚焦回归

1. 新增 `tests/01_unit_tests/test_tc0025_caller_info.py`：用无 `test_tc` 特判的固定调用文件验证直接调用、包装调用、行号、16 字符截断和日志行内容；用配置对象验证普通路径不触发完整调用链。
2. 更新 `tests/01_unit_tests/test_tc0019_call_chain.py`：异常注入改为替换当前 frame 获取 Seam，继续断言 `[调用链异常]`；其余调用链、多层调用和开关用例保持。

### 8.2 固定 benchmark

验证资产放在 `docs/05_预研/验证_20260915/`，使用标准库 `time.perf_counter_ns`，固定直接调用与一层包装调用两组输入，先预热再重复测量；输出至少包含 `sys.version`、平台、配置开关、消息/参数、预热次数、重复次数、计时范围、每次耗时统计、返回位置和日志内容断言。基线取变更前版本，候选取变更后版本，二者使用同一命令参数和解释器。报告和原始结果由 design-plan/implementation 写入 Issue 目录，solution-decision 不提前宣称运行结果。
